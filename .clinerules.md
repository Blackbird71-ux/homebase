# Cline Rules — VS Code App Building with Docker Deployment

## 🔍 Before You Start

### 1. Audit the Existing Codebase First

**Required checks before any implementation:**
- Review folder structure, entry points, existing components, routes, and data models
- Read `package.json` / `requirements.txt` / `pyproject.toml` to understand dependencies
- Check for `.env.example` or config files to understand environment variables in use
- Identify the project's coding style (linting config, formatter, naming conventions)
- **Examine Docker files:** `Dockerfile`, `docker-compose.yml`, `docker-entrypoint.sh`
- Note any Windows-to-NAS specific paths or volume mappings

### 2. Design Before Building

**Planning requirements:**
- Summarize what already exists that's relevant to the task
- Propose implementation plan with specific files to create or modify
- **Explicitly state how changes affect Docker builds** (layers, dependencies, entrypoint)
- Wait for user confirmation before proceeding with any changes

### 3. Docker/WSL-NAS Considerations

**Always include in planning:**
- How changes impact the Docker build process (layer caching, image size)
- Volume mount requirements for NAS deployment
- Windows path conversions vs Linux paths in containers
- Environment variables needed for both dev (Windows) and prod (NAS)
- Entrypoint script modifications if adding new startup requirements
- Multi-platform compatibility (amd64/arm64 for NAS devices)

## 🛠️ During Development

### General Rules
- Work carefully with **no regressions** — verify existing functionality remains intact
- **Only modify files directly related to the task** — no refactoring unrelated code
- Maintain all existing functionality — do not break what already works
- Ensure **backward compatibility** for functions, APIs, or data schemas
- Match project's existing **error handling patterns** (try/catch, toast notifications, logging)
- Do **not hardcode secrets or API keys** — use environment variables and `.env` files
- Before adding new dependency, check if existing library already covers the need

### Docker-Specific Development Rules
- **Never hardcode paths** — use environment variables or Docker volume mounts
- Test path handling both in Windows dev environment and Linux container
- Update `docker-compose.yml` if adding new services, networks, or volumes
- Document any new environment variables in `.env.example`
- Ensure `docker-entrypoint.sh` remains executable after modifications
- Consider startup order when adding dependencies between containers

### Performance & Quality
- Avoid blocking main thread; use async/await, lazy loading, or workers
- Handle all UI states: **loading, error, empty, and success**
- Run project's linter and formatter before finishing (ESLint, Prettier, Ruff, Black)
- Consider container resource limits (CPU, memory) for performance-critical features

### Accessibility
- New UI elements must include proper labels, ARIA attributes, keyboard navigation
- Maintain sufficient colour contrast (WCAG AA minimum)
- Test with screen readers when adding significant UI components

### Security
- Never log or expose sensitive data
- Sanitize user inputs; validate on both client and server
- Follow existing auth/permission patterns for new routes or actions
- **Docker security:** Don't run containers as root, use non-root user in Dockerfile
- Scan for vulnerabilities in new dependencies

## 🤖 Sub-Agent Workflow

### Parallel Processing
- Deploy sub-agents in parallel for independent tasks to speed up work
- Each sub-agent must **check back** before merging output into main codebase
- Sub-agents must run tests and confirm module working before reporting complete
- The orchestrating agent performs final **integration test** after all sub-agents finish

### Sub-Agent Requirements
- Each sub-agent must document their Docker-related changes
- Agents working on different containers must coordinate network communication
- Test independently before integration

## ✅ Testing

### Required Testing Protocol
- Test all new code paths, including edge cases
- **Test for existing users** — no breaking changes to current workflows or data
- Verify feature works across relevant environments:
  - **Dev:** Windows native (if applicable)
  - **Docker dev:** Docker Compose on Windows
  - **Staging:** Docker on target NAS architecture
  - **Production:** NAS deployment

### Docker-Specific Testing
- Build image successfully: `docker compose build`
- Start services: `docker compose up -d`
- Verify container health checks pass
- Test volume persistence across container restarts
- Check network connectivity between containers
- Verify environment variable injection
- Test with Windows line endings (CRLF) vs Linux (LF) in mounted files

### Regression Testing
- Confirm existing routes/APIs still respond correctly
- Verify database migrations are reversible
- Ensure file permissions in volumes remain correct

## 🌿 Git & Worktrees

### Commit Guidelines
- Use descriptive commit messages explaining *what* and *why*
- Do not mix unrelated changes in a single commit
- **Update all relevant worktrees** when finished
- Note which files changed and why in completion summary

### Docker File Commit Rules
- Commit `Dockerfile`, `docker-compose.yml`, `docker-entrypoint.sh` together when modified
- Document breaking changes in commit message (e.g., environment variable removals)
- Tag commits that change Docker configuration

## 🔁 Rollback & Recovery

### Before Starting
- Note current state of any files to modify (including Docker files)
- Document current image tag/version for rollback reference

### Production Issues
- If something breaks in production, document what to revert
- Prefer feature flags for large or risky changes
- **Docker rollback:** Keep previous image tagged, use `docker compose up --no-build`

### Emergency Procedures
- Have `docker-compose.yml` backup ready
- Document steps to revert to previous working state
- List commands to check container health and logs

## 🐳 Docker Build & Deployment Quick Reference

### 🚨 DEPLOYMENT WORKFLOW (NO GIT)

**Build from `c:\Appdev\HomeBase` on Windows, then copy to NAS:**

1. All source files live in `c:\Appdev\HomeBase` — this is the single source of truth
2. Build the Docker image or create a tar from `c:\Appdev\HomeBase`
3. Copy tar to NAS and deploy
4. **Migrations:** SQL files must be added to `prisma/migrations/<timestamp>_<name>/migration.sql`
   - The container entrypoint runs `prisma migrate deploy` on startup, which picks up any new migration folders
   - No need to run `prisma migrate dev` locally — just create the SQL file manually in a properly-named directory

# Development build with cache
docker compose build

# Force rebuild without cache
docker compose build --no-cache
